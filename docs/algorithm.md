# 스바다 알고리즘 설명서 (시연용)

스바다에는 알고리즘이 4개 있습니다. 발표할 때는 **① AI 가격 → ② 가격 매칭 → ③ 선호도 학습 → ④ 홈 피드·알림** 순서로 설명하면 자연스럽습니다.

| # | 이름 | 코드 | API |
|---|---|---|---|
| ① | AI 가격 분석 파이프라인 | `ai/AiPriceService`, `ai/PriceSanitizer` | `POST /api/ai/analyze` |
| ② | 가격 매칭 "내 물건과 바꿀 만한 물건" | `recommend/RecommendationService#matches` | `GET /api/items/{id}/matches` |
| ③ | 선호도 학습(온보딩 + 행동) | `user/PreferenceService` | `PUT /api/me/preferences` |
| ④ | 홈 피드 · 새 물건 매칭 알림 | `RecommendationService#feed`, `#notifyNewItemMatches` | `GET /api/feed` |

점수 계산식은 모두 `recommend/ScoreMath.java` 에 **순수 함수**로 모아 두었고 `ScoreMathTest` 로 검증합니다(11장: 기대값과 실제값 비교).

## ① AI 가격 분석 파이프라인

```
사진 ──▶ (1) Gemma 호출 ──▶ (2) JSON 정규화 ──▶ (3) 범위·반올림 보정 ──▶ (4) 앱 내 시세 블렌딩 ──▶ 저장
              │ 실패/미설정
              └──────────▶ 기준가 추정(fallback): 카테고리 평균 중고가 × 상태 감가율
```

**(1) Gemma 호출** — 순서: Google AI Studio(`gemma-4-26b-a4b-it`) → 로컬 Ollama(`gemma4:e4b`) → fallback.
프롬프트는 "JSON 하나만 출력하라"고 형식을 강제합니다(`AiPrompt.java`).

```json
{"title":"에어팟 프로 2세대","category":"DIGITAL","condition":"LIKE_NEW",
 "price_krw":150000,"price_min_krw":130000,"price_max_krw":170000,
 "confidence":0.8,"reason":"정품 케이스 포함, 사용감 적음. 신품가의 약 55%","tags":["에어팟","이어폰"]}
```

**(2) 정규화** — AI가 `"digital"`, `"디지털기기"`, `"15만원"` 처럼 답해도 enum·정수로 바꿉니다. 판매자가 직접 고른 카테고리·상태(힌트)가 있으면 그것을 우선합니다.

**(3) 보정** — AI 답을 그대로 믿지 않습니다(4장 5.2 "환각을 알고 답 확인하기").
- `min ≤ price ≤ max` 가 아니면 ±20% 로 다시 잡음
- 범위는 최소 ±5%, 최대 0.4배~2.5배
- 가격은 500원 ~ 5,000만원 사이
- 반올림: 1만원 미만 500원 단위, 10만원 미만 1,000원 단위, 그 이상 5,000원 단위

**(4) 앱 내 시세 블렌딩** — 같은 카테고리·상태 물건이 앱에 3개 이상 있으면 그 중앙값을 섞습니다.

```
최종가 = (1 − α) × AI가 + α × 앱 내 중앙값,     α = 0.3 × min(1, 표본수 / 10)
```
예) AI가 48,000원, 같은 종류 5건의 중앙값 40,000원 → α = 0.15 → 0.85×48,000 + 0.15×40,000 = **46,800 → 47,000원**

> 왜 중앙값? 평균은 100만 원짜리 하나만 섞여도 크게 흔들리지만, 중앙값은 튀는 값에 강합니다.
> 왜 최대 30%? AI가 사진을 직접 본 판단을 주(主)로 두고, 앱 시세는 보정용으로만 씁니다.

**보안 규칙(7장)**: 등록 요청에 `price` 를 넣으면 **400 UNKNOWN_FIELD**. 가격은 서버가 `analysisId` 의 결과에서만 복사하고, 남의 분석 결과를 쓰면 403.

## ② 가격 매칭 — "내 물건과 바꿀 만한 물건"

내 물건 화면의 **"비슷한 가격대 매칭"** 버튼(등록 직후에도 자동으로 열림)이 부르는 알고리즘입니다. 3단계로 동작합니다.

### 1단계: 후보 생성 (DB가 거른다)
```sql
SELECT * FROM items
 WHERE status = 'AVAILABLE' AND owner_id <> :me
   AND ai_price BETWEEN :price*0.5 AND :price*2      -- 인덱스 idx_items_status_price(status, ai_price)
 LIMIT 300
```
가격이 반~두 배 밖인 물건은 점수를 계산할 필요도 없으므로 DB 인덱스로 먼저 잘라 냅니다.

### 2단계: 점수 계산 (0 ~ 100점)

```
매칭 점수 = 0.40·가격유사도 + 0.25·내선호 + 0.20·상대선호(상호성) + 0.10·신선도 + 0.05·상태유사도
```

| 요소 | 식 | 의미 |
|---|---|---|
| 가격 유사도 (40%) | `0.75·exp(−(ln(p₂/p₁))² / 2·0.35²) + 0.25·IoU(가격범위)` | 가격이 비슷할수록 1 |
| 내 선호 (25%) | `내 선호도[후보 카테고리] + (관심 키워드가 제목에 있으면 0.3)` | 내가 원하는 종류인가 |
| 상대 선호 (20%) | `max(상대 선호도[내 카테고리], 상대가 '바꾸고 싶은 카테고리'로 지정했으면 1)` | 상대도 내 물건을 원할까 |
| 신선도 (10%) | `exp(−경과일 / 14)` | 오래된 글은 이미 거래됐을 확률이 높다 |
| 상태 유사도 (5%) | `1 − |상태등급차| / 4` | 새것 ↔ 고장품 같은 불균형 방지 |

**가격 유사도를 "차이"가 아니라 "비율의 로그"로 보는 이유**
1만 원 vs 2만 원과 10만 원 vs 20만 원은 둘 다 "두 배"이므로 같은 거리여야 공정합니다. `ln(p₂/p₁)` 은 비율을 거리로 바꿔 줍니다.

| 가격 비율 | 1.1배 | 1.2배 | 1.5배 | 2배 |
|---|---|---|---|---|
| 가우시안 점수 | 0.96 | 0.87 | 0.51 | 0.14 |

**IoU(Intersection over Union)**: AI가 준 가격 범위 두 개가 겹치는 길이 ÷ 합친 길이. 가격 하나만 볼 때보다 AI의 불확실성까지 반영됩니다.

**상호성(20%)이 핵심 아이디어**: 중고 "거래"는 한쪽만 원하면 되지만, 물물"교환"은 **양쪽이 서로 원해야** 성사됩니다(경제학의 '욕망의 이중 일치'). 그래서 상대의 선호까지 점수에 넣었습니다.

### 3단계: 다양성 보정
점수 순으로 하나씩 고르되, 같은 카테고리가 이미 k개 뽑혔으면 `점수 × 0.85ᵏ` 로 비교합니다(MMR 간소화). 상위 10개가 전부 같은 종류로 채워지는 것을 막습니다.

### 예시 계산 (시연 데이터와 비슷한 상황)

내 물건: **블루투스 이어폰** · 디지털 · 거의 새것 · AI가 50,000원 (범위 40,000~60,000)
나는 온보딩에서 **취미/게임** 을 골랐다.

| | 후보 A: 게임 타이틀 | 후보 B: 블루투스 스피커 |
|---|---|---|
| 가격(범위) | 55,000원 (45~65k) · 사용감 적음 | 90,000원 (70~110k) · 거의 새것 |
| 가격 유사도 | 0.75×0.964 + 0.25×0.600 = **0.873** | 0.75×0.244 + 0.25×0 = **0.183** |
| 내 선호 | 취미/게임 = **1.0** | 디지털 = **0** |
| 상대 선호 | 상대가 '디지털로 바꾸고 싶어요' = **1.0** | 관심 없음 = **0** |
| 신선도 | 1일 전 = **0.931** | 5일 전 = 0.700 |
| 상태 유사도 | 1등급 차이 = **0.75** | 같음 = 1.0 |
| **합계** | 0.349+0.25+0.20+0.093+0.038 = **93점** | 0.073+0+0+0.070+0.05 = **19점** |

앱 화면에는 점수와 함께 **이유 칩**("비슷한 가격대 (+10%)", "상대가 디지털기기(으)로 바꾸길 원해요", "방금 올라온 물건")과 요소별 막대가 그대로 보입니다. → 추천이 "왜" 나왔는지 설명 가능.

## ③ 선호도 학습 — 온보딩 + 행동

사용자마다 카테고리별 가중치 `w ∈ [0, 1]` 을 `user_preferences` 테이블에 저장합니다.

**(1) 온보딩(앱 첫 실행)** — "바꾸고 싶은 물건 종류", "관심 키워드", "희망 가격대"를 고릅니다.
- 고른 카테고리 → `w = 1.0` (source = ONBOARDING)
- 다시 설정할 때 뺀 카테고리 → `w = 0.2` 로 낮춰 약한 관심으로 남김
- 키워드는 최대 10개, 제목에 들어 있으면 선호 +0.3

**(2) 행동 학습** — 행동할 때마다 `w ← w + rate × (1 − w)`

| 행동 | rate | 의미 |
|---|---|---|
| 남의 물건 상세 보기 | 0.03 | 약한 신호 |
| 채팅 시작 | 0.10 | |
| 바로 바꾸기 요청 | 0.20 | 강한 신호 |
| 교환 성사 | 0.30 | 가장 강한 신호 |

`(1 − w)` 를 곱하므로 **1을 절대 넘지 않고, 높을수록 천천히 오릅니다**(포화 곡선).
예) 관심 없던 카테고리(0)를 5번 구경하면 0.141, 0.2 인 카테고리에 교환 요청을 보내면 0.2 + 0.2×0.8 = 0.36.

**콜드 스타트**: 온보딩을 건너뛰어 선호가 하나도 없으면 모든 카테고리를 0.5로 보고 가격·신선도·인기로 추천합니다(`feed-v1(cold-start)`).

## ④-A 홈 피드 — "나를 위한 교환 추천"

```
피드 점수 = 0.40·선호도 + 0.30·가격적합도 + 0.15·신선도 + 0.15·인기도   → 다양성 보정
```

- **가격 적합도**: 내가 올린 물건들 중 가격이 가장 잘 맞는 것과의 가격 유사도(②와 같은 식). 아직 올린 물건이 없으면 온보딩 희망 가격대 안이면 1, 밖이면 가장 가까운 경계와의 가우시안.
- **인기도**: `ln(1 + 조회수 + 3×교환요청수) ÷ ln(1 + 후보 중 최대값)` — 로그를 씌워 조회수 많은 글 하나가 피드를 독점하지 않게 합니다.
- 이미 내가 교환을 요청한 물건에는 "요청함" 표시.

## ④-B 새 물건 매칭 알림 (푸시)

물건이 등록되어 **DB 커밋이 끝난 뒤**(`AfterCommit`) 별도 트랜잭션에서 실행합니다.
1. 새 물건 가격의 **0.77 ~ 1.3배**(로그 거리로 대칭, 약 ±30%) 물건을 가진 사람을 찾는다
2. 그 사람이 이 카테고리를 원하는가? (선호도 ≥ 0.6 또는 '바꾸고 싶은 카테고리'에 포함)
3. `관심도 × 가격 가우시안` 상위 **5명**에게만 `MATCH_SUGGESTED` 알림 → WebSocket 또는 FCM 푸시

5명으로 제한한 이유: 모든 사람에게 보내면 알림이 스팸이 되어 사용자가 알림을 끕니다.

## 발표 때 받을 만한 질문과 답

- **왜 머신러닝 모델이 아니라 가중합인가?** 사용자가 적은 초기 서비스는 학습할 데이터가 없습니다(콜드 스타트). 가중합은 데이터가 없어도 동작하고, 화면에 이유를 그대로 보여 줄 수 있습니다. 데이터가 쌓이면 가중치를 교환 성사율로 학습하는 방향으로 확장할 수 있습니다.
- **가중치 0.40/0.25/0.20 은 어떻게 정했나?** "교환은 가격이 맞아야 시작된다"를 가장 크게, 그다음 양쪽의 선호를 두었습니다. 상수로 분리해 두어(`W_PRICE` 등) 시연 데이터로 바꿔 보며 조정할 수 있습니다.
- **AI가 엉뚱한 가격을 말하면?** ③ 보정 단계에서 범위를 자르고, 앱 시세를 최대 30% 섞고, 신뢰도(confidence)를 화면에 보여 줍니다. 판매자는 등록 전에 결과를 확인합니다.
- **AI 서버가 꺼져 있으면?** fallback 으로 카테고리 기준가 × 상태 감가율을 쓰고, 화면에 "기준가 추정 (AI 미연결)"이라고 표시합니다. 시연이 멈추지 않습니다.
